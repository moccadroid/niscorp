A mutation's column value may now be `{ $scope: "key" }`, as a filter's value already could: an entry stamps the server's moment with `archived_at: { $scope: 'now' }`, from a `now` the host puts in scope per request (under moss, the app's `scope` seam), instead of a time the client sends in context or a function written only to stamp it. Every statement of a batch binds the same value; a host that supplies none gets `missing_scope` and nothing is written. Who a row belongs to is written by a `set` rule, never by an entry: a column value may not be a `$scope` value naming a key the policy binds (`userId`, a tenant's id), a `$lookup` whose `where` compares with such a key, or a `$returned` copy of a column a write rule fills or pins. vex refuses such a write with `invalid_dsl` before anything runs (`identityValueMisfits(def, bound)` says which; `boundByBehaviors(behaviors)` gives the keys and columns behaviors bind, as a `ScopeBound`), and moss refuses such an entry at boot, publish and refresh, counting `userId` whether or not a rule names it. Any other `$scope` value gets past the policy no more than a `$context` value does: a `set` column is written by the engine over it, and a `match` column written on an update must be one the rule allows, unless the host turns that check off with `checkMovedRows: false`. A constant `$context` or `$scope` value written into a `json` column of an `insertEach` now binds as JSON text, as it does in an `insert`; before, node-postgres sent an array as a Postgres array literal, which the column refused, or, for an empty array, stored as an empty object. vex DOCS has a new "The server's time" section; nisc's AGENTS.md says to stamp a write's moment this way.
