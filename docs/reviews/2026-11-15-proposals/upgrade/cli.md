# Upgrading: @niscorp/cli (the "Owner to confirm" fixes P3, P8, P9)

Three changes an app can see. None changes a table or a grammar: no migration, no snapshot, no `strata.lock.json` moves. No lab app had to change.

### @niscorp/cli — `nisc export` refuses a path whose file cannot be made, or would land outside the export's folder, before touching anything

- Before: on Windows, an app whose `paths` (perhaps read from database rows) gave `/a:b` emptied `out/`, wrote `/`, then died with a raw `ENOENT … mkdir 'out\a:b'` stack (exit 1), leaving half a site. A path `/z\..\..\escape` with `--out ../site1/sub/deep` wrote `site1/escape/index.html`, outside the export's folder, and exited 0.
- Now: every export is first written whole into a fresh folder of its own (`.nisc-export-<process>-<id>`, beside `out/` in the app's folder, or inside a folder named with `--out`). Only when every file was made is the export's folder touched. `/a:b` on Windows prints `nisc: the path "/a:b" cannot be written here (ENOENT). Nothing was written.`, exit 1, and `out/` is exactly as it was. `/z\..\..\escape` on Windows prints `nisc: the path "/z\..\..\escape" cannot be written here (its file would be outside …). Nothing was written.`, exit 1, and nothing is written anywhere. Which names fail is the system's answer, not a list: `/about.`, `/about ` and `/con` export on Windows 11 as before, and `/a:b` on Linux or macOS still writes `a:b/index.html`. The default `out/` is then emptied and written by the same code as before, so its files and their modes are unchanged; the fresh folder beside it only checked that every file can be made (the export is written twice: once there, once into `out/`). A `.nisc-export-…` folder that a killed export leaves in the app's folder or in the `--out` folder is removed by the next export.
- Who notices: an app on Windows whose `paths()` returns a path containing `\..\` or a character Windows refuses in a file name (`:`, `*`, `"`, `<`, `>`, `|`). Nobody can rely on a page landing outside the export's folder.
- What to do: nothing. If an export now stops with `cannot be written here`, the path named is one no static host could serve from that folder; leave it out of `paths()` or spell it as a folder name.
- Breaking: yes (pending consolidation) — an export that exited 0 on Windows (writing outside its folder) now exits 1.
- Affected apps: none found. Lab apps: only `apps/lab/mythos/package.json:9` (`"export": "nisc export"`) and `apps/lab/atrium/src/dev/nisc-check.ts:29,34` export; their paths are page paths with no `\` or `:`. Outside the repo: AnimaApp, anima-finance and mira have no export step (`package.json` scripts: `dev`, `build`, `start`, `check`, `test`).

### @niscorp/cli — `nisc start` no longer remembers compressed answers

- Before: `nisc start` kept every compressed answer marked `immutable`, keyed by encoding, path and `last-modified` — not the query — and never forgot one. An app route `/thumb` answering `cache-control: public, max-age=31536000, immutable` by `?user=`: `/thumb?user=alice`, then `/thumb?user=bob` → Bob got "thumbnail of alice". A repeated asset answer came whole, with a `content-length`.
- Now: every answer is compressed as it streams, as every answer not marked `immutable` already was. `/thumb?user=bob` gets Bob's thumbnail. The bytes a browser decodes are the same; a repeated `/assets/…` answer comes without `content-length` (as the first one always did) and costs the compression again: brotli quality 5 on a 371 kB bundle is about 5.5 ms, once per browser, since `/assets/` files are kept a year.
- Who notices: an app server route under `nisc start` that answers `immutable` with text (HTML, JS, CSS, JSON, SVG) and a body that depends on the query or the caller; or a client that read `content-length` on a repeated asset answer.
- What to do: nothing.
- Breaking: yes (pending consolidation) — nothing, unless something relied on a repeated `immutable` answer being the first answer's bytes with a `content-length`.
- Affected apps: none. Lab apps: no route sets `immutable` (the one match, `apps/lab/lyra-integrations/src/integrations/stripe/client.ts:13`, is a comment). Outside the repo: AnimaApp's `src/server/media/index.ts:442` answers `private, max-age=86400, immutable`, but with `image/webp`, which was never compressed or remembered; its answers are unchanged. anima-finance and mira set no `immutable`.

### @niscorp/cli — the shape check reports a reach spelt another way, and passes `<const>`

- Before: the shape check (`@niscorp/cli/shape`, run as an app's `src/dev/shape-check.ts`) matched spellings: `session.roles` failed rule 11, but `const { roles } = session` passed; `Intl.NumberFormat` failed rule 9, but `const { NumberFormat } = Intl` and `new globalThis.Intl.DateTimeFormat()` passed; `location.pathname` failed rule 4, but `const { pathname } = window.location` passed; `document.querySelector` failed rule 2, but `window['document'].querySelector(…)` passed; `import { wordsOf } from '../app/helpers'` failed the `data` rule, but `import * as helpers` (`helpers.wordsOf(1)`), `export { wordsOf } from '../app/helpers'` and `await import('../app/helpers')` passed. `<const>['a', 'b']` failed rule 16 as "a <T> assertion".
- Now: the rules that fail are exactly as they were. A second reading asks the compiler what each name refers to and prints, for each of those other spellings, one line such as `[info] rule 9: src/server/when.ts:1 Intl, the global one — another spelling of what the rule fails on; reported, not failed`. A line is left out when a rule already fails the same name in that file, and when the app's `allow` names that file for that rule. The exit code never changes because of these lines; if the second reading cannot run, one `[info]` line says so. `<const>[...]` passes rule 16, as `as const` does. The cli README now says which spellings fail and which are only reported. The check takes a second or two longer on a large app (lyceum, relay, lyra).
- Who notices: an app that runs the shape check sees new `[info]` lines where its code reaches past a rule by another spelling. An app whose `allow.style` names a file only because of a `<const>` assertion sees that allowance fail as "has nothing to allow".
- What to do: nothing for the `[info]` lines (read them; fix the reach or leave it). If an `allow.style` entry now "has nothing to allow", delete it. Note that an `allow` entry added only to quiet an `[info]` line fails the same way, since an allowance has to excuse something a rule fails.
- Breaking: yes (pending consolidation) — nothing, unless an app's `allow.style` names a file only because of a `<const>` assertion.
- Affected apps, each run against the old and the new check (actions left out, so only the source rules compare): no lab app runs the shape check, and on every lab app (lyceum, encore, relay, mythos, fable, lyra, atrium) the new check prints the same `[pass]`/`[fail]` lines and 0 new `[info]` lines. Outside the repo: anima-finance runs it (`src/dev/shape-check.ts`); the new reading finds `src/ui/navigate.tsx:50` (`window.location`), which its `allow.address` already names, so it prints nothing new. mira runs it (`src/dev/shape-check.ts`): 0 new lines. AnimaApp does not run it; if it did, it would see three `[info]` lines: `src/ui/navigate.tsx:65` (`const { pathname, search, hash } = window.location`), `src/server/billing/gate.ts:20` and `src/server/boot.ts:166` (`roles` read off moss's identity result). No app has a `<const>` assertion.
