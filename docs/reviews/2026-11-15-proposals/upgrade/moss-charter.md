# Upgrading: moss and charter (P-M7, P-C7)

Two changes. Neither changes a grammar, a table, a type or an exported name.

### @niscorp/moss — a revoked session's socket closes within one `sessionRevalidateMs` plus the verifier's answer time, however many sockets are open
- Before: every `sessionRevalidateMs` a pass asked the app's `session` verifier about one live socket, waited for the answer, then asked about the next. A pass took as long as all the answers added together. With 200 open sockets, a verifier that answers in 20 ms and `sessionRevalidateMs: 500`, a socket whose token was revoked stayed open for about 6.7 seconds. Three sockets of one browser that present the same token were three calls.
- Now: a pass asks the verifier once for each token, every token at the same moment, and waits for the answers until the next pass is due. In the same example the revoked socket closes after about 520 ms (one interval plus the verifier's 20 ms). Three sockets that present one token are one call. An answer that comes after the next pass was due is still acted on when it comes. A pass that came due while the previous one was still waiting starts as soon as that one ends, instead of an interval later. The log line "could not be asked about N of M connection(s)" still counts sockets. The log line for an answer that fails after its pass went on is written once for each token and now reads "could not be asked about a token after its pass went on. Its connections stay open and are asked again" (it said "about a connection … It stays open").
- Who notices:
  - Any app with many signed-in sockets: the verifier can now be called more often than before. The most it is called is once for each distinct token every interval, all at the start of the pass. Where a pass used to take longer than the interval, the old code called it less: in the example above, about 114 calls in 4 seconds, one at a time, become about 1394 calls in 4 seconds, up to 200 at once (about 28 a second become about 350 a second).
  - An app on `session: 'sessions'` (AnimaApp, anima-finance, mira, lyceum): each pass, every 60 seconds by default, sends one `SELECT … FROM sessions` for each distinct token at once. On PGlite or a small pool they queue ahead of the requests that arrive in that moment.
  - An app whose `runtime.session` is a function of its own that calls a service with a strict limit on calls at once, or that counts its calls.
- What to do:
  - Small apps: nothing.
  - With many signed-in sockets on `'sessions'`: watch request latency around each pass; if it shows, raise `sessionRevalidateMs` or the pool size.
  - A verifier of your own with a limit on calls at once: queue inside the verifier (for example a small semaphore around the service call); moss has no option for it.
- Breaking: yes, pending consolidation (the verifier sees more calls at once, and where passes used to run over the interval more calls in total; no result changes for a verifier that answers each call).

Apps checked:
- Lab apps: none affected. lyceum runs `session: 'sessions'` (`apps/lab/lyceum/src/server/runtime.ts:21`, `postgres-runtime.ts:18`), atrium, encore, lyra, lyra-admin and relay's server run `'dev-open'`, which answers every call at once without a query, so they are unaffected (`apps/lab/atrium/src/server/runtime.ts:26`, `apps/lab/encore/src/server/runtime.ts:29`, `apps/lab/lyra/src/server/runtime.ts:27`, `apps/lab/lyra-admin/src/service.ts:19`, `apps/lab/relay/src/server/runtime.ts:36`). relay's expiry check passes an in-memory verifier with `sessionRevalidateMs: 250` (`apps/lab/relay/src/dev/expiry-check.ts:72`); it passes unchanged.
- AnimaApp: `session: 'sessions'` (`src/server/runtime.ts:22`, `:34`). Nothing to change in code; with many signed-in sockets, watch request latency around each pass.
- anima-finance: `session: 'sessions'` (`src/server/runtime.ts:32`, `:39`). Nothing to change in code; with many signed-in sockets, watch request latency around each pass.
- mira: `session: 'sessions'` (`src/server/runtime.ts:24`, `:31`). Nothing to change in code; with many signed-in sockets, watch request latency around each pass.

### @niscorp/charter — a top-level `deny` beside an `actions:` section takes away when the role is resolved without verifying
- Before: `{ r: { actions: ['crm.*'], deny: ['crm.deal.delete'] } }` resolved through `resolveRole` / `resolvePrincipal` to everything under `crm.*`, `crm.deal.delete` included: only the `actions:` section was read. `verifyCharter` refuses such a role (`ambiguous-selection`), so moss never boots it.
- Now: the same role resolves to everything under `crm.*` except `crm.deal.delete`: the top-level `deny` is taken away as well as the section's own `deny`. A top-level `allow` beside an `actions:` section still grants nothing, since reading it would grant more than either selection says. A role that extends it (`c: { extends: ['r'] }`) no longer gets `crm.deal.delete` from it either. `verifyCharter` refuses the role as before, and now checks that top-level `deny` like any other, so a charter already refused can report more lines for it: `dead-deny` when it matches nothing (`{ r: { actions: ['crm.*'], deny: ['hr.nothing'] } }`), `orphan` for an action it leaves no role granting, and a re-allow warning for a child that grants back what it takes away.
- Who notices: only code that calls `resolveRole` or `resolvePrincipal` on a charter it never passed through `verifyCharter`, where a role has both an `actions:` section and a top-level `deny`. Under moss nothing changes: such a charter is refused at boot.
- What to do: nothing. If you resolve charters without verifying, run `verifyCharter` and fix the role it names: move the `deny` into the `actions:` section (`actions: { allow: ['crm.*'], deny: ['crm.deal.delete'] }`).
- Breaking: yes, pending consolidation (a narrowing to what was written; nothing unless code relied on the top-level `deny` being dropped).

Apps checked: no charter in the lab apps (`apps/lab/*/src/app/charter/charter.ts`, `apps/lab/atrium/src/admin/app/charter.ts`, `apps/lab/lyra-admin/src/app/charter.ts`), AnimaApp, anima-finance or mira has a top-level `deny` at all; every `deny` in them is inside a `data:` section (`apps/lab/relay/src/app/charter/charter.ts:18`, `:39`). The direct callers of `resolvePrincipal` (AnimaApp `src/server/billing/gate.ts:15`, `src/server/media/uploads.ts:32`, `src/server/billing/signatures.ts:42`, `src/server/billing/membership.ts:402` and its dev checks; atrium `src/server/assistant/knowledge.ts:111`; relay `src/dev/engine.ts:22`, `src/dev/charter-check.ts`, `src/dev/smoke.ts:62`) see the same result as before.
