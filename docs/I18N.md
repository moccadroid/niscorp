# Internationalisation

**Status:** built and running in lyra (German, `de`). 2026-08-13.
**Moved into the renderer** 2026-08-14 — see "Where the swap runs".
**Regions dropped** 2026-08-16 — a locale is a bare language tag. See "One
offer per language".
**Spans:** `prism`, `vex`, `nova`, `moss`, `apps/lab/lyra`.

This is the design record. It says what was built, what was rejected and why,
what it deliberately does not cover, and where to pick it back up. Read the
"Four channels" section first — everything else hangs off it.

---

## What the problem actually was

A survey of lyra found **~470 user-facing strings across seven origins**, and
they do not all live where you would hope:

| Origin | Count | Reachable from a layout walk? |
|---|---:|---|
| Layout props (`label`, `title`, `placeholder`, column labels, Select options) | ~610 | yes |
| Action `title` (Sheet chrome, catalog) | ~90 | yes |
| Words a **vex mapping** manufactures (`standingLabel`, `sessionStateText`) | ~40 | **no** — authored inside a query |
| The navigation table (`nav/sections.ts`) | 31 | no — app data |
| Layout text children | ~15 | yes |
| The automation vocabulary (`compose.ts` → seeded rows) | ~35 | no — rendered as row data |
| Strings the app composes server-side (the greeting, role labels) | ~10 | no — built, not authored |

Plus the half that is not translation at all: **dates, money, numbers**.

### The bug that was already shipping

`format.prism.ts` hand-rolled a currency table (`EUR: '€'`) and joined
symbol-then-amount, and prism's `$date` used dayjs tokens with no locale. So
lyra rendered `€45` and `Fri 14 Mar` for every studio in every country — and it
was seeded with an **Austrian** studio. One currency and one language disagree
across three countries:

| locale | money | number |
|---|---|---|
| `de-AT` | `€ 45,00` | `1 234,5` |
| `de-DE` | `45,00 €` | `1.234,5` |
| `de-CH` | `EUR 45.00` | `1'234.5` |
| `en-GB` | `€45.00` | `1,234.5` |

No symbol table gets this right. `Intl` already knows it. This was fixed first,
independently of any translation work, because it is a live correctness bug.

That table is history, not the offer: the app stores `de` and `en` and takes
each language's own convention (`89,00 €`, `€89.00`). See "One offer per
language" for why the regional tags went.

## Four channels

There is no single mechanism that covers all seven origins, and pretending
otherwise is how an i18n layer ends up 90% done forever. There are **four**, and
each one owns a category the others structurally cannot reach.

```
                    ┌─────────────────────────────────────────────┐
  authored layouts  │  1. THE RENDER PASS                         │
  action titles     │     nova's RENDERER, where a RenderNode is  │
  component text    │     minted · source phrase → translated     │
  closed-set        │     phrase, keyed on the English source     │
  *_display words   └─────────────────────────────────────────────┘
                    ┌─────────────────────────────────────────────┐
  dates             │  2. THE FORMATTING OPS                      │
  money             │     prism $localeDate/$localeMoney/         │
  numbers           │     $localeNumber · Intl, at the source     │
                    │     unbounded cardinality — no dictionary   │
                    └─────────────────────────────────────────────┘
                    ┌─────────────────────────────────────────────┐
  the greeting      │  3. APP-COMPOSED STRINGS                    │
  role labels       │     server/phrases.ts · same book, looked   │
                    │     up in TypeScript, name concatenated     │
                    └─────────────────────────────────────────────┘
                    ┌─────────────────────────────────────────────┐
  email templates   │  4. SEEDED CONTENT — NOT DONE               │
  recipe bodies     │     the studio's own words, not ours        │
                    └─────────────────────────────────────────────┘
```

### 1. The render pass — nova's renderer

A host names a book; nova's renderer swaps prose as it builds the tree:

```ts
createShell({ …, phrases, phraseKeys })     // or the same two fields
                                            // on any RenderContext
```

Nova stays **language-blind**, exactly as it is surface-blind: it holds no
dictionary and knows no languages. The host injects both, the same way it
injects the transform evaluator.

**Proseness is decided by the KEY, never by the value.** A render tree is mostly
not prose — it carries person names, ids, css values, tone words, icon names and
row data. The host declares which keys carry prose:

```ts
phraseKeys: {
  props: [...DEFAULT_PHRASE_KEYS.props, 'role', 'phrase', 'why', 'sentence'],
  suffixes: ['_display', '_label'],
}
```

The `_display` suffix rule is what makes the words a **query** manufactures
translatable. lyra's vex entries already wrote every display string to a
`*_display` field for their own reasons; naming that convention once here means
forty field names never have to be listed.

Matching is at **any depth** inside a prop value, which is what makes a spec
prop work: a `Table`'s `columns: [{ label }]` and a `Select`'s
`options: [{ label }]` are the same rule as a bare `label`.

## Where the swap runs

**In the renderer, at the two points where a `RenderNode` is minted** —
`layout/renderer.ts`, the resolved-props line and the text-child branch. Every
tree in the system comes out of `renderLayout` / `renderLayoutFromStore`, and
there are exactly three callers: the action runtime (instance trees), the shell
(chrome and canvas layouts), and `<Nova.Layout>`.

It ran in moss until 2026-08-14, over the finished tree, between
`flattenRenderTree` and `JSON.stringify`. That worked and was wrong in one
specific way: **it was only ever going to work for moss-served apps.** A pure
nova app has no equivalent moment — React pulls each action instance's tree
lazily inside `ActionSlot`, so `useCanvasRenderTree` sees the canvas chrome and
nothing inside it. Translating there would have meant an i18n implementation
per adapter — react, dom, tty, ink, and every one after them — which is N
copies of one rule, drifting.

Moving it one layer down buys four things:

- **Zero adapter code, permanently.** Adapters *consume* `RenderNode`s; they
  never mint them. A Vue adapter costs no i18n work. This is the test for
  whether something belongs in nova: does adding it change the adapter
  contract? This does not.
- **Pure nova is localisable.** No moss, no server, no wire.
- **No second traversal.** The swap happens on a value the renderer already
  holds — one lookup instead of a full re-walk of everything just built.
- **A rule the tree pass could not express.** By the time a tree exists, a
  literal text child and a bound one are the same plain string. The renderer
  still knows which was authored, so **a bound text child is never
  translated** — closing a hole where `children: ['$.person.name']` would
  offer a member called "Pass" to the dictionary. Bound *props* are still
  translated, because that is the whole `_display` mechanism; there, the key
  is what protects data.

**Counted phrases are filled in every language, including the source one.** A
`{ phrase, slots }` at a prose key is closed at render whether or not there is
a book, so no component ever meets the raw shape. lyra's kit used to carry its
own filler for exactly this and no longer does.

### What is still in `@niscorp/nova/i18n`

- `harvestLayout` / `harvestDefinition` / `harvestDefinitions`, `missingFrom` —
  extraction, unchanged.
- `translateRenderTree` — for whoever holds a tree they did **not** render: a
  replayed frame, a fixture, a hand-built test tree. No longer the main road.
  One deliberate difference from the renderer: an empty book short-circuits and
  returns the same tree, patterns included.
- `fillPhrase(value)` — a counted phrase held as **data** rather than shown. For
  checks and exporters reading engine output directly, upstream of any render.
- `DEFAULT_PHRASE_KEYS`, `isBinding`, `isPhrase`, `matcherFor`.

### `setPhrases` / `getPhrases`

`shell.setPhrases(book)` replaces the book live and reaches instances that are
**already mounted** — a runtime asks for the book at each render rather than
holding one from spawn, which is why the shell's `i18n` seam is a function.
`getPhrases` is its reader, for overlaying rather than replacing (a studio that
calls its members "athletes" — roadmap item 6).

This does not remove the need for a rebuild when the *host* composed text in the
old language (lyra's greeting, seeded labels). It reaches what nova renders, and
nova cannot know what a host built before handing it over.

**Withdrawing a book is the SOURCE LANGUAGE, not switching i18n off.** A shell
is "language-bearing" from the moment it is given a book or a key set, and
`setPhrases(undefined)` cannot un-answer that. The distinction is not cosmetic:
a shell that stopped doing i18n would leave a counted phrase as the
`{ phrase, slots }` object it travels as, and the adapter would be handed a
structure where a word belongs — a crash, not a missing translation. Only a
shell that never mentioned language pays nothing, which is still the common
case.

### Two bugs this design had, both found by running it

Worth recording, because both were invisible to the unit tests that existed:

1. **`useRenderTree` cached instance trees on data identity alone.** A language
   change touches no instance's data, so every screen already open kept the
   words it was mounted with while the chrome around it switched. The cache key
   now includes the book. Regression test:
   `test/react/i18n-live-switch.test.tsx` — the runtime-level test passed
   throughout, which is exactly why an adapter-level one was needed.
2. **The activation rule read the current cell instead of the config**, so
   withdrawing a book disabled pattern-filling and put a raw object on the
   glass. Fixed as described above; covered in `test/i18n/render-pass.test.ts`.

### 2. The formatting ops — `prism`

`$localeDate`, `$localeMoney`, `$localeNumber`. `locale` is **required** on all
three; a default renders plausible nonsense for everybody it is wrong for.

- `$localeMoney` takes the minor-unit divisor **from the currency**, not a
  hardcoded 100 — JPY has no minor unit and dividing it would be a
  hundredfold error.
- `$localeDate` reads a DATE-only value (`"2026-03-14"`) as **UTC**. That string
  is UTC midnight, and formatting it in any zone west of Greenwich prints the
  13th. Every date column has this shape, so the trap is handled once in the op
  rather than rediscovered at forty call sites.
- Formatters are cached per resolved argument tuple; constructing an `Intl`
  formatter costs ~100× using one, and a mapping over a thousand rows would
  otherwise build a thousand.

### 3. App-composed strings

`"Guten Morgen, Maren"` cannot go through the render pass — a name makes its
cardinality unbounded. `server/phrases.ts` exports `greetingFrom`, which takes a
book the caller already holds, looks the fixed half up in it, and concatenates
the name. It takes the book rather than fetching one for the same reason it
lives in one place: a second fetch is how the same sentence gets to disagree
with itself.

It lives in one place because it originally lived in **two** (`inputs` for the
opening paint and `nav.identity` for the confirming read) and they drifted the
moment one of them learned about languages — the screen greeted in German on
load and in English a tick later. That was a real bug caught by the check.

### 4. Seeded content — deliberately not done

A recipe's email subject and body reach the screen as `Input` **values**, and
`value` is not a prose key. Translating one would display German and **save
English**. That line is the difference between chrome and content: this system
owns the words the application says, never the words a studio wrote.

## How the locale and the words get to a shell

Rows, twin of `themes` — the same argument applies: a studio's look and a
studio's language are both things its owner decides and no deploy should be
involved in.

Both halves are **rows read over the session's own wire**, not resident tables.
The books were `BY_LOCALE` in `server/phrases.ts` (every phrase for every
language, held at boot) until the shell seams became async; they are vex entries
now, and the locale rides on the identity record rather than on `scope`.

```
studios.locale ('de')             phrases (locale, source, text)
        │                         integrations.phrasebook (approved)
        │                                    │
  identity.entries.ts                 language.entries.ts
  identity/studio → record.locale     phrases/book · phrases/integrations
        │                                    │
        ├──► app.ts scope() ─────────────────┤   → engine-side, unforgeable
        │      (clock only; locale comes     │
        │       off the identity record)     │
        │        └──► vex mapping $.scope.locale
        │                 └──► $localeMoney / $localeDate
        │                                    │
        └──► app.ts phrases({ identity }) ───┘
                 └──► bookOverWire(): integrations' words first,
                      the app's own OVER them
                          └──► moss build() → createShell({ phrases })
                                   └──► the RENDERER → every tree
```

`phrases/locales` answers which languages exist; `world.languages` unions the
**source** locale on top, because the source language has no rows by
construction and a studio reading English must still be offered English.

Two decisions worth restating:

**One offer per language.** The phrase table is keyed `de` because Vienna and
Hamburg read the same sentences, and a studio stores that same `de` — so a book
is selected by equality and nothing in the app widens a tag.

This replaced a fan-out. `world.languages` used to turn one German book into
three offers (`de-AT`, `de-DE`, `de-CH`) on the argument that words are per
language but formatting is per region. The argument is true and it was still
wrong: what it put in front of a studio owner was a picker with four entries,
three of them German, differing only in where a currency symbol sits. Nobody
opens a studio app to answer that question. The cost of dropping it is that
`Intl` now formats from the language's own convention — an Austrian studio
reads `89,00 €` rather than `€ 89,00` — and the picker reads *Deutsch* and
*English*, once each.

The region half is **gone, not hidden**: `studios.locale` is `CHECK (locale ~
'^[a-z]{2}$')`, so nothing can store a country tag and drift a second German
back into the list. `studios.country` already exists for anything that genuinely
needs a country; formatting is not it.

**Locale sits on the studio, not the person.** Language is the more personal of
the two, but a studio is where the shared surface lives — the desk screen two
people share, the words on a member's notice. Per-person is the obvious next
move and needs one more column and a `COALESCE`.

### Changing the language

The write is an ordinary vex mutation (`studio/set-language`), engine-scoped like
every other. Its **consequence** is `world.relanguage`, a `fn:` endpoint that
re-reads the rows and **rebuilds** every shell at that studio.

A rebuild, not a `refresh()`. Refresh re-registers definitions in place and keeps
mounted instances — right for a changed artifact, wrong here, because `inputs`
composed the greeting, the nav labels and the identity card in the old language,
and only a rebuild re-derives them. The settings screen is therefore disposed
mid-step; it says "Switching language — one moment." and stops.

**A rebuild alone is not enough, and the failure is silent.** The locale rides on
the IDENTITY record (`identity/studio` reads `studios.locale`), moss caches those
per principal, and a rebuilt shell re-derives itself from whatever the cache
still says. So the write lands, every shell is faithfully rebuilt, every one of
them re-reads the old language, and the screen repaints in German having done
exactly what it was told. `world.relanguage` therefore calls
`invalidateTenant(studioId)` **before** the reset loop — tenant-local, like the
add-on reaction in `app.ts`, because one studio's language says nothing about
anybody else's.

The general rule this is an instance of: **anything derived from a cached
identity record must forget the record, not just rebuild what read it.** The
same applies to timezone, currency and the studio's own name, all of which sit
on that record beside the locale.

## Why keying on the source string

The alternative is a key per string (`label: '@t.people.add'`). Both work; they
cost differently.

Keys are precise and make every layout in the application **unreadable** — a
file stops saying what it draws. Source strings leave the layouts as the readable
English they already are and move the whole problem to one walk.

The price is real: **English-as-key cannot distinguish two senses of one word.**
"Book" the verb and "Book" the noun are one key here and two words in German.
When that bites, the answer is not to abandon the pass — it is to disambiguate
that one string at its author site. The `phrases.context` column exists for
exactly that and is unused so far; a `$t` directive in nova's resolver
(`DIRECTIVES` in `shared/bindings/resolve.ts`) is the natural place to name it.
The two compose. This layer is what makes the other one **optional** rather than
mandatory.

### The collision guard rail

A member called "Pass" must not be renamed the day somebody sells one. Three
things prevent it, and all three matter:

1. **Proseness is decided by the key.** `person_name` is marked prose by
   nothing, so the book is never consulted for it — even though "Pass" is a key
   in it. Tested in both `test/i18n/i18n.test.ts` and
   `test/i18n/render-pass.test.ts`.
2. **A bound text child is data.** A text position has no key to protect it, so
   the renderer uses what only the renderer knows: whether the string was
   authored or resolved. `children: ['$.person.name']` is never offered to the
   book; `children: ['People']` is. The moss-era pass could not draw this line —
   by the time a tree exists, both are the same plain string.
3. **The harvester reads authored artifacts, never a rendered tree.** What
   enters the dictionary is only ever a string a person wrote, so a value that
   happened to be on screen the day somebody ran the harvest cannot get in.

## Rejected

| Option | Why not |
|---|---|
| **`@t` extras scope** (`'@t.people.title'` resolved by the renderer) | Works with zero schema change and would have cost ~750 layout edits, for no capability the pass lacks. Subsumed by pass + `$t`. |
| **`$t` directive, as the primary mechanism** | Needs a `LayoutNodeSchema` union addition for text positions and 750 edits. Kept in reserve for params/plurals/disambiguation, where it is genuinely better. |
| **Locale as a served variant** (per-language `ActionDefinition` copies through moss's ring-2 seam) | Doctrinally the cleanest — AGENTS.md rule 11 says per-principal UI is a served variant — and zero runtime cost. Held in reserve, now further out of the money: the swap is no longer a per-frame walk over a finished tree, it is one lookup on a value the renderer already holds. Does not reach vex-born strings, so it was never a complete answer on its own. |
| **The swap in the adapters** (translate in React's `RenderNodeView`, and again in dom/tty/ink) | The obvious place, and it is one implementation per adapter forever. Rejected for the reason the renderer was chosen: an adapter renders a `RenderNode`, and i18n that changes the adapter contract is i18n every future adapter inherits. |
| **A `DISTINCT locale FROM phrases` query for the switcher's options** | Wrong in an instructive way: the **source** language has no rows, by construction. A studio reading English would be offered every language except the one it needs. The offer is server knowledge (`world.languages`). |
| **Localising dayjs** | Would mean shipping a locale pack per language into prism, which has no business knowing which languages exist. `Intl` is already in the platform. |

## Package changes

- **prism** — new `$localeDate` / `$localeMoney` / `$localeNumber`
  (`src/ops/intl.ops.ts`, `src/schemas/ops/intl.schema.ts`). No new dependency.
  Docs: `DOCS.md` § Locale-Aware Formatting.
- **vex** — the mapping source widened from `{ result }` to
  `{ result, context, scope }` (`src/engine/runtime.ts`). Additive. This is what
  lets a mapping — where a row becomes words — know the reader's language.
  **It does not touch the cache**: vex caches the query *plan* (`dsl` +
  `prismIr`), never rows, and a compiled mapping holds the lookup rather than
  the looked-up value, so one cache entry serves every language.
- **nova** — `@niscorp/nova/i18n` holds extraction (`harvest*`, `missingFrom`),
  the phrase-key vocabulary, `translateRenderTree` for foreign trees, and
  `fillPhrase` for patterns held as data. The **swap** lives in
  `layout/renderer.ts`; `i18n/swap.ts` is the shared value-level engine both it
  and `translateRenderTree` call, deliberately free of any layout import.
  `RenderContext`, `RenderOptions`, `ShellConfig` and `<Nova.Layout>` each gain
  `phrases` / `phraseKeys` / `onPhraseMiss`, all optional. `Shell` gains
  `setPhrases` / `getPhrases`.
- **moss** — two manifest seams, `phrases(principal)` and `phraseKeys`, resolved
  at build and handed to `createShell`. `frame()` and `attach()` no longer
  translate anything.

**Both absent = not doing i18n, and free** — no matcher is built and a
`{ phrase, slots }` passes through as the object it is. moss therefore withholds
an empty book rather than passing `{}`. **Keys without a book is the source
language:** nothing is translated, patterns still close.

## Working on it

```bash
pnpm --filter lyra exec tsx src/dev/phrase-harvest.ts de
```

Reports coverage and lists what is missing. `--emit` writes a seed-shaped
skeleton — how the German book was first filled in. It reads four sources:
the action catalog, the nav table, the automation vocabulary, and two explicit
lists (words born in vex mappings, and strings the app composes).

```bash
pnpm --filter lyra exec tsx src/dev/language-check.ts
```

Drives the real shells: Lumen (`de`) and North Rock (`en`) in one
deployment, asserting that the words, the money and the dates all differ while
the **action set is identical** — if a language ever changed which screens
exist, something branched on it and rule 11 is broken.

`treeOf()` and `servedTo()` in `dev/world.ts` still differ, but no longer for
the reason they used to. A shell now renders in its reader's language, so
`treeOf` turns the book **off deliberately** (`getPhrases` → `setPhrases`
→ restore) and answers in the language the application was authored in. That is
what a structural check wants: asking "does the roll open" should not require
knowing what "People" is in German. A check about **words** must use
`servedTo()`, which attaches a real connection and keeps what comes down it.

Coverage today: **548/548** fixed phrases translated. Four "assembled" phrases
(`"12 of 20"`) carry digits, have unbounded cardinality, and are handled at
their point of assembly in `format.prism.ts` instead.

## Where to pick it back up

Roughly in order of value:

1. **Plurals.** The one gap that is a **type** change rather than a content one:
   `Phrasebook` is `Record<string, string>`, one source → one target. German was
   a lucky first language (two forms, like English), so `{n} of {total}` covers
   it. Polish has three, Arabic six. `Intl.PluralRules` is in the platform and
   the pattern op is the right host for it. Worth doing **before** there is a
   second consumer of the exported type.
2. **Anonymous principals get the source language.** The login screen is the one
   screen whose reader is unknown. Guessing from `Accept-Language` would make it
   the one screen in the app whose language is a guess — but it is also the
   first thing a German speaker sees. Probably: a per-deployment default locale,
   not a header sniff.
3. **Per-person locale.** One column on `studio_people`, a `COALESCE` where the
   identity entry reads `studios.locale`, and a control on the member's own
   screen. The rest already works — `phrases(principal)` is per principal.
4. **`$t` for disambiguation.** English-as-key cannot separate two senses of one
   word; `phrases.context` is in the schema for exactly this and unused.
5. **Seeded content** (channel 4). Recipe email subjects and bodies. Needs a
   decision about whose words those are — probably per studio, written by them,
   which makes it a content feature rather than an i18n one.
6. **Per-studio vocabulary.** A studio that calls its members "athletes" is the
   same mechanism as a language: an overlay on top of the phrasebook.
   `shell.getPhrases()` is the reader that makes overlaying possible.
7. **A second language that is not German.** The real test of the harvester is
   a language with different plural rules and a non-Latin script.

## Known gaps, stated plainly

- **Plurals.** One target string per source string — see item 2 above.
- The login screen and everything an anonymous principal sees is English.
- Recipe email templates are English (channel 4, by design).
- `phrases.context` is in the schema and unused — no disambiguation yet.
- **Prose living in an action's `data:`** is invisible to the harvest, which
  walks layouts and entries but not defaults. A words-bearing options array
  declared in `data` is untranslatable-in-practice and uncounted, so the gate
  can read 548/548 while a screen shows English. Tracked in
  `docs/plans/lyra-defects.md` §10.1.
- **Typographic variants are separate keys.** `'…'` vs `'...'`, `'` vs `'`.
  `swap` tries exact then trimmed, and nothing normalises beyond that.
- **A component's own default copy** never enters a `RenderNode` tree, so no
  pass reaches it. Default copy must be authored as a prop, or the kit
  translates it itself. This was equally true of the moss-era pass.
- The harvester over-collects `data` defaults holding tokens and ids; the
  exclusions are an explicit list in `dev/phrase-harvest.ts` with reasons. They
  cannot be mistranslated (they land at non-prose keys), they were only noise in
  the report — and a report with permanent noise stops being read.

## Showroom — the proof that this is nova's

`apps/showroom` has **no moss in its dependencies**. Six stories under the
**i18n** section run on pure nova: no server, no wire, and no i18n code in any
adapter. Their books are a plain TypeScript file (`stories/i18n/books.ts`,
German + French) beside lyra's row-backed one, which is the demonstration that a
`Phrasebook` is `Record<string, string>` and where it came from is the host's
business.

`i18n` is a story **kind** rather than a category, so the whole area lands in
one sidebar segment instead of being split across Shells and Layouts by an
implementation detail. The nova-side guide is `packages/nova/I18N_DOCS.md`,
served in the showroom's DOCS list beside the layout, action, shell and react
guides. (This file stays the cross-package design record — prism, vex, moss and
lyra included.)

| Story | Shows |
|---|---|
| Phrasebook | The whole wiring: `createShell({ phrases })`, plus `setPhrases` reaching a mounted instance |
| Prose keys | A member surnamed “Pass” beside a product called “Pass”, with `Pass → Zehnerblock` in the book. Four identical strings, two translate |
| Spec props | Column labels two levels down, `*_display` words a query made, `person_name` untouched beside them |
| Counted phrases | `{n} of {total}` → `{n} von {total}`, `{n} left` → `noch {n}` (the hole changes sides), and holes closing with no book at all |
| Harvest | `harvestDefinition` live with author sites — including a trigger-written string and a conditional's unrendered branch — then `missingFrom`, then `onPhraseMiss` at runtime |
| Locale formatting | The same screen at `de` and `en`: one book each, and the money, the numbers and the dates differ in both — plus `de-AT` resolving to no book at all, because nothing widens a tag any more |
