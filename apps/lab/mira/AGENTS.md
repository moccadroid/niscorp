# mira

A nisc application. **The rules it is built by are `node_modules/@niscorp/nisc/AGENTS.md`** — read all of it before changing anything here (it is there once the app's dependencies are installed). It is the rulebook for the nisc version this app has installed, and `STYLE_GUIDE.md` sits beside it. The grammars it names — a layout node, an `ActionDefinition`, a Prism config, a charter, a Vex DSL — are in each package's own `README.md` and `DESIGN.md`, under `node_modules/@niscorp/<name>/`.

What is particular to this app:

- **Its decisions are in PLAN.md.** What was answered when it was made, what was derived, and what is still open. An open decision point is asked before anything is built on it, never resolved silently.
- **It is led by a model: every message is answered with a screen composed from the app's actions**, behind moss, drawn with React.
- **Where things go:**

```
src/app/action-catalog.ts  every action, and `placeable`: the ones the model may put on a screen
src/app/screens.ts  the screens in the dock: canvases shown together; the first is the one the app opens on
src/app/arrangements.ts  how an answer is laid out: layouts for the frame’s `answers` region, and what each is for
src/server/compose/ the message loop: the open screen read, Jev's pass, gpt-oss-120b composes, the plan is placed
                    catalog.ts       what the model is given to place: the `placeable` actions, the reads, the writes
                    screen.ts        the open screen, read
                    pick.ts          Jev's pass
                    composer.agent.ts  the composer: a cortex agent
                    knowledge.ts     what it is told: its instructions, the catalog as producers, the run’s input
                    reply.schema.ts  what it replies, each field described
                    answer.ts        what refuses a reply, and the answer a reply is turned into
                    layout.ts        arrangements and the grids the model writes, as layouts
                    plan.ts, history.ts  the answer as a plan, its inks, and the stack of them, kept as the person's rows
                    deck.ts          the stack as the overview draws it
                    index.ts         the functions the dock calls
src/server/identity/ who a person is: the sign-in link (signin.request, /login), the mail, the role read off `people`
src/server/models/  the models, from .env
src/server/runs/    each model's part in a message recorded as a run, and the line the server logs for it
src/db/         your tables, as a strata sequence: people, and the sign-in links
src/app/        ARTIFACTS ONLY — the manifest (app.ts), the charter, the actions, the shell, the reads and writes (vex/)
src/server/     the environment (runtime.ts: Postgres or PGlite), the boot, how a screen is drawn (document.ts)
src/ui/         the kit — the only renderer code, with src/main.tsx, the terminal entry: kit.tsx the
                components, kit.css the look, target.ts which updates are moves and how each is drawn:
                motion/ the stage of card copies an answer moves on, the sideways slide back and
                forward take, the dock's travelling words; the overview's zoom is a view transition
src/dev/        the checks (`npm run check`) — a new feature adds its own
nisc.config.ts  how the app boots and how its screens are drawn, for the `nisc` command

                by `npm run strata verify`, never by hand
```

- **How it runs:** `npm run dev`, `npm run build`, `npm run check`, `npm start` — all of them the `nisc` command — and `npm run strata status` for the grammars. With `DATABASE_URL` in `.env` it runs on Postgres (`docker compose up -d` stands one up here), and `npx nisc migrate` applies the tables as a deploy step (`--check` tries it and rolls it back); without it, on an in-memory PGlite. The checks always run on PGlite.
- **Who gets in** (PLAN.md D13): the people in `people`. The owner is `MIRA_OWNER`, let in at boot; the owner invites the rest from the People screen. Nobody signed in holds only `signin.door`: their address, and a link mailed to it (`signin.request`), redeemed once at `/login`. In `npm run dev`, `/dev/as/<an invited address>` signs in on this machine.

## How the model leads

The model answers from the screen open when a message arrives and from the conversation: the person's last ten messages and what it replied, from this shell and before it (PLAN.md D15). The answer is one screen and never scrolls: cards that do not fit fold to their titles but one, the one the answer changed or the one tapped, which scrolls inside itself (the kit's Grid). One dock stays at the bottom, the last layer (`src/app/actions/ask/dock.action.ts`). It holds a chip naming the answer shown by its title and where it stands ("The charter · 2/5"), with back and forward beside it, and under it what the model said back when an answer left the screen as it was; the line to ask in; and the **screens** (`src/app/screens.ts`: canvases shown together, opened without asking, as a card's link opens one) — Start, People, and the Conversation (`ask.conversation`), every message and what was said back as a chat, the oldest first, opening at the newest, each message opening the answer it got. The overview draws each answer by its cards as nova drew them when the person last left it (`drawn`, kept on the answer's row; the kit's Picture draws them again), folded as the screen folds them; a picture swiped up there, or closed with its ×, closes its answer: it leaves the stack for good and stays in the Conversation, and the first screen cannot be closed. The arrow keys and a sideways swipe are back and forward too. The chip opens every answer side by side (`ask.deck`, pushed onto the `overview` canvas over the answer), each a small picture of its screen with what was asked and what the model said it did; while it is open, back and forward and the arrows move the pick, and Enter, the chip or a tap opens it, Escape closes it. A person types in the line, and the answer is a screen: up to six canvases — an action opened with an input, and why it is there — on the areas `a`–`f`. Each answer to a message has an ink of its own, a card keeps the ink of the answer that put it there, and the answer knows which cards it changed or put where nothing was, which decides the one open when cards fold (PLAN.md D14); the server draws the frame's region with only the areas the answer fills, each told its row, its column, its ink and what the answer did to it (`drawnRegion`, in `layout.ts`). The first screen is the first in the stack, and what the app opens on for somebody who was given no answer yet; it welcomes, so an answer asked on it starts from an empty screen. The line grows with what is typed: Enter sends, Shift and Enter start a new line. A screen already in the stack is gone back to, not stacked again. **The stack lasts** (PLAN.md D8): every message is kept as a row of the person's through vex (`answers/keep`, in `history.ts`) with what was said back — an answer that put up a screen with its layout and the grammars it was written at (rule 19), one that did not with the answer or screen it was asked on — and a new shell reads the last 50 that put up a screen (`answers/recent`) and the last 100 messages (`answers/said`) before anything is shown, and opens on the newest answer; the dock asks for it as it mounts. A row that no longer reads is left out with a line in the log, and the rest stay.

- **The message loop is `src/server/compose/`**, the function `ask`:
  1. **The open screen is read** (`screen.ts`), area by area, the words too: each canvas's action and intent; its input as it stands, with what the person pressed, ticked or picked in what the input carries; and what else its live data holds beyond what it was opened with — a list as its count and its first three rows, ids left out; a line being typed. Before anything else is shown — an answer, a screen, back or forward — the screen as it stands is kept with the answer it is on, as a browser keeps a page's form: going back shows it as the person left it.
  2. **Jev's pass** (`pick.ts`): over the message and the open screen, how likely each action, read, write and screen of the catalog belongs in the answer, in about 200 ms (what it was measured to be worth is PLAN.md D6). Only a hint: the model decides, and only what the pass finds likely (0.5 or more) is shown to it. Whether a canvas is still wanted is the model's to say (PLAN.md D11).
  3. **gpt-oss-120b composes, as a cortex agent** (`composer.agent.ts`, `knowledge.ts`, `reply.schema.ts`, `answer.ts`). Its producers give it the catalog — each action the person holds that the model may place, with its input's JSON Schema, each read with the rows it answers and the values it is asked with, each write, the screens, the arrangements with where each puts its areas, and what Mira is (ABOUT MIRA: how many cards a screen holds, the stack, the dock) — and cortex's OUTPUT SCHEMA, the envelope with the reply's own JSON Schema in it, in the part of the prompt that never changes; the run's input is the conversation, the open screen, Jev's picks as a hint, and the message. What each field of the reply means is said on the schema (`.describe()`), never in prose beside it (nisc rule 15). It answers with cortex's envelope: its `reasoning` first, then its `response` — what it says back to the person, one or two sentences addressed to them that answer what they asked, read apart from the screen: kept in the Conversation, and under the chip only when the screen does not change, for the screen is where it answers: with one of the app's screens when one shows what was asked, an action, or words on a card — then its `data`, the reply: its `title` — what the answer is, in at most four words, the name the chip and the stack give it — then **the areas that change** (PLAN.md D10): each a canvas moved there from another area (`keep`), a canvas, words (`say`: an answer to read — an explanation, steps, a list — or what no action shows), or nothing (`drop`); an area it leaves out stays as it is, unless the arrangement it gives has no such area — and then the room, when the one on screen will not do: an arrangement, or a grid of its own. Or it replies with one of the app's screens as it is (`screen`). The reply is checked whole — every action in the catalog, every input against its action's schema, every read and write one the app ships, every value a read is asked with present and none it does not take, every field a write saves present, every area in the arrangement, nothing kept from an empty area, nothing shown twice — by the agent's `output.validate`, and one that does not hold, or does not fit the schema, is corrected inside the same run with what is wrong with it: three answers at most (cortex's `outputRetries`). About 1 s.
  4. **The answer is laid out,** in the arrangement on screen unless the model gives another (`src/app/arrangements.ts`), or a grid it writes (`grid`: how many columns, and the areas in the order they are drawn, each with its span), which the server turns into the layout. The server puts it into the region through the shell's draft (`session.draft`), where moss checks it: the frame with the arrangement in it, one layout taken again for each answer and kept nowhere.
  5. **The plan is placed by the dock,** with nova's `reconcile`: each area holds exactly what the plan lists for it. A canvas that stays keeps its instance and what the person did to it; a card the model writes again is written where it stands. A canvas written onto a screen holds its whole input — what it leaves out is its action's default (`opened`, in `catalog.ts`) — so a card written where another was keeps nothing of it (PLAN.md D12). An answer that changes nothing adds nothing to the stack; the chip still names what was asked. What the model said back is under the chip until the next message. A screen opened, or back or forward pressed, while an answer streams in is what is shown: that answer is no longer placed.
  6. **The answer streams in.** Cortex hands the composer the reply as solid parses it, while the model writes it. Once an area's entry is followed by the next, or by the room, it is finished, and it is placed in the room on screen if its own checks pass; another room, or a screen, comes with the whole reply; the dock re-reads the answer so far (`answers.current`) whenever the message `answer-moved` says it moved. Whether the whole reply holds is checked when it ends. A correction, or a run that ends without an answer, puts the screen back as it was.
- **A message that gets no screen leaves the screen as it is,** and the line says why: the model's reply did not fit, it could not be reached, or there is no key.
- **Jev may take 2 s and the model 8 s.** A Jev pass given up leaves the model to answer alone.
- **Every message is recorded as a run for each model it went to,** through moss (`session.recordRun`): `mira.jev` and `mira.compose`, each with its provider and model, the tokens it spent (`reported: false` where signal estimated them), its steps and how long it took — for the composer, cortex's run meta — and whether it ended in an answer. The server logs a line for each (`src/server/runs/`).
- **An action you add is small, with one purpose:** it says what it shows (`description`), and declares what the model may open it with as a JSON Schema written with zod, every field described; the model's answers are checked against that same schema (`z.fromJSONSchema`). A read or a write it names must be one the app ships, asked with the values it takes. The ones the model may place are `placeable`, in `src/app/action-catalog.ts`.
- **The model never presses anything.** It opens cards with an input — a form filled in — and only the person saves.
- **The keys are in `.env`** (`.env.example` lists them): `GROQ_API_KEY` (gpt-oss-120b; without it, a message is answered with a notice saying so), `TYPESAFE_API_KEY` (Jev; without it there is no Jev pass), `MIRA_OWNER`, `RESEND_API_KEY` (without it a link is written to the server's log), `MAIL_FROM`, `PUBLIC_URL` (where a mailed link points) and `DATABASE_URL`.
- **The model is offered what the person may use:** the placeable actions they hold, the screens whose every action they hold, and the reads and writes vex lists for them when they ask it (`/api/vex`, as the person).
- **`src/dev/compose-check.ts` runs the loop offline**, with a scripted Jev and a scripted model (`src/dev/scripted.ts`), on words, screens and actions the app does not have — so it holds whatever actions the app ships.

## How to proceed from here

First the interview: PLAN.md's open items, each answered or delegated by name (the rulebook's "Before any code").

**Then build in PLAN.md's order of work,** each step checked before the next: your tables, reads and writes; your actions, each placeable one in `placeable` and every one granted in the charter's `actions`; your screens; and a check for each feature in `src/dev/`.
