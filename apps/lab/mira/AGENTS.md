# mira

A nisc application. **The rules it is built by are `node_modules/@niscorp/nisc/AGENTS.md`** — read all of it before changing anything here (it is there once the app's dependencies are installed). It is the rulebook for the nisc version this app has installed, and `STYLE_GUIDE.md` sits beside it. The grammars it names — a layout node, an `ActionDefinition`, a Prism config, a charter, a Vex DSL — are in each package's own `README.md` and `DESIGN.md`, under `node_modules/@niscorp/<name>/`.

What is particular to this app:

- **Its decisions are in PLAN.md.** What was answered when it was made, what was derived, and what is still open. An open decision point is asked before anything is built on it, never resolved silently.
- **It is led by a model: every message is answered with a screen composed from the app's actions**, behind moss, drawn with React.
- **Where things go:**

```
src/app/action-catalog.ts  every action, and `placeable`: the ones the model may put on a screen
src/app/screens.ts  the screens in the dock: canvases shown together; the first is the one the app opens on
src/app/arrangements.ts  how an answer is laid out: layouts for the frame’s `answers` region, and what each is for
src/server/compose/ the message loop: the screen read, gpt-oss-120b composes, the plan is placed
                    catalog.ts       what the model is given to place: the `placeable` actions
                    screen.ts        the screen as the person sees it, read off nova
                    composer.agent.ts  the composer: a cortex agent
                    knowledge.ts     what it is told: its instructions, the catalog as producers, the run’s input
                    reply.schema.ts  what it replies, each field described
                    answer.ts        what refuses a reply, and the answer a reply is turned into
                    layout.ts        the arrangements screens are laid out in, and the grid of an answer's cards
                    plan.ts, history.ts  the answer as a plan, its inks, and the stack of them, kept as the person's rows
                    deck.ts          the stack as the overview draws it
                    index.ts         the functions the dock calls
src/server/identity/ who a person is: the sign-in link (signin.request, /login), the mail, the role read off `people`
src/server/models/  the models, from .env
src/server/runs/    each model's part in a message recorded as a run, and the line the server logs for it
src/db/         your tables, as a strata sequence: people, and the sign-in links
src/app/        ARTIFACTS ONLY — the manifest (app.ts), the charter, the actions, the shell, the reads and writes (vex/)
src/server/     the environment (runtime.ts: Postgres or PGlite), the boot, how a screen is drawn (document.ts)
src/ui/         the kit — the only renderer code, with src/main.tsx, the terminal entry: kit.tsx the
                components, kit.css the look, target.ts which updates are moves and how each is drawn:
                motion/ the stage of card copies an answer moves on, the sideways slide back and
                forward take, the dock's travelling words; the overview's zoom is a view transition
src/dev/        the checks (`npm run check`) — a new feature adds its own
nisc.config.ts  how the app boots and how its screens are drawn, for the `nisc` command
strata.lock.json  the grammar versions the source is written at (rule 20) — moved only
                by `npm run strata verify`, never by hand
```

- **How it runs:** `npm run dev`, `npm run build`, `npm run check`, `npm start` — all of them the `nisc` command — and `npm run strata status` for the grammars. With `DATABASE_URL` in `.env` it runs on Postgres (`docker compose up -d` stands one up here), and `npx nisc migrate` applies the tables as a deploy step (`--check` tries it and rolls it back); without it, on an in-memory PGlite. The checks always run on PGlite.
- **Who gets in** (PLAN.md D13): the people in `people`. The owner is `MIRA_OWNER`, let in at boot; the owner invites the rest from the People screen. Nobody signed in holds only `signin.door`: their address, and a link mailed to it (`signin.request`), redeemed once at `/login`. In `npm run dev`, `/dev/as/<an invited address>` signs in on this machine.

## How the model leads

The model answers from the screen open when a message arrives and from the conversation: the person's last ten messages and what it replied, from this shell and before it (PLAN.md D15). The answer is one screen and never scrolls: cards that do not fit fold to their titles but one, the one the answer changed or the one tapped, which scrolls inside itself (the kit's Grid). One dock stays at the bottom, the last layer (`src/app/actions/ask/dock.action.ts`). It holds a chip naming the answer shown by its title and where it stands ("The charter · 2/5"), with back and forward beside it, and under it what the model said back when an answer left the screen as it was; the line to ask in; and the **screens** (`src/app/screens.ts`: canvases shown together, opened without asking, as a card's link opens one) — Start, People, and the Conversation (`ask.conversation`), every message and what was said back as a chat, the oldest first, opening at the newest, each message opening the answer it got. The overview draws each answer by its cards as nova drew them when the person last left it (`drawn`, kept on the answer's row; the kit's Picture draws them again), folded as the screen folds them; a picture swiped up there, or closed with its ×, closes its answer: it leaves the stack for good and stays in the Conversation, and the first screen cannot be closed. The others close the gap from where each was on screen: the one picked stays where it is, and when it is the one closed, the one after it takes the middle, or the one before it at the end. The arrow keys and a sideways swipe are back and forward too. The chip opens every answer side by side (`ask.deck`, pushed onto the `overview` canvas over the answer), each a small picture of its screen with what was asked and what the model said it did; while it is open, back and forward and the arrows move the pick, and Enter, the chip or a tap opens it, Escape closes it. A person types in the line, and the answer is a screen: up to six cards in reading order, in one to three columns — each an action opened with an input, and why it is there, or words — the first on the area `a`, the next on `b`, and so on. Each answer to a message has an ink of its own, a card keeps the ink of the answer that put it there, and the answer knows which cards it changed or put where nothing was, which decides the one open when cards fold (PLAN.md D14); the server draws the frame's region with only the areas the answer fills, each told its row, its column, its ink and what the answer did to it (`drawnRegion`, in `layout.ts`). The first screen is the first in the stack, and what the app opens on for somebody who was given no answer yet; it welcomes, so an answer asked on it starts from an empty screen. The line grows with what is typed: Enter sends, Shift and Enter start a new line. A screen already in the stack is gone back to, not stacked again. **The stack lasts** (PLAN.md D8): every message is kept as a row of the person's through vex (`answers/keep`, in `history.ts`) with what was said back — an answer that put up a screen with its layout and the grammars it was written at (rule 19), one that did not with the answer or screen it was asked on — and a new shell reads the last 50 that put up a screen (`answers/recent`) and the last 100 messages (`answers/said`) before anything is shown, and opens on the newest answer; the dock asks for it as it mounts. A row that no longer reads is left out with a line in the log, and the rest stay.

- **The message loop is `src/server/compose/`**, the function `ask`:
  1. **The screen is read off nova** (`screen.ts`), as the person sees it: from the dock, the answer shown, where it stands in the stack and what was said back under the chip, and the screens; and the answer's cards in reading order, the first screen's too: each card's title as nova drew it, its action and intent; its input as it stands, with what the person pressed, ticked or picked in what the input carries; and what else its live data holds beyond what it was opened with — a list as its count and its first three rows, ids left out; a line being typed. Before anything else is shown — an answer, a screen, back or forward — the screen as it stands is kept with the answer it is on, as a browser keeps a page's form: going back shows it as the person left it.
  2. **gpt-oss-120b composes, as a cortex agent** (`composer.agent.ts`, `knowledge.ts`, `reply.schema.ts`, `answer.ts`). Its instructions say who it is: Mira, an assistant. Its producers give it, in the part of the prompt that never changes, the catalog — each action the person holds that the model may place, with its input's JSON Schema, and the screens — and what Mira is (ABOUT MIRA: how many cards a screen holds, the stack, the dock), with cortex's OUTPUT SCHEMA, the envelope with the reply's own JSON Schema in it; then, for each message, today's date and who it is talking to (the owner, or somebody invited), and THE SCREEN. The run's input is the chat itself (PLAN.md D15): the person's last ten messages, each followed by what was said back to it, the oldest first, and the message last. What each field of the reply means is said on the schema (`.describe()`), never in prose beside it (nisc rule 15). It answers with cortex's envelope: its `reasoning` first, then its `response` — what it says back to the person every time, one or two sentences addressed to them that answer what they asked, read apart from the screen: kept in the Conversation, and under the chip only when the screen does not change, for the screen is where it answers: with one of the app's screens when one shows what was asked, an action, or words on a card — then its `data`, the reply: its `title` — what the answer is, in at most four words, the name the chip and the stack give it — then one of the app's screens as it is (`screen`), or **the screen after the answer** (PLAN.md D10): how many columns, as on screen when left out, and every card on it in reading order — a card on the screen now, kept by its title (`keep`), a card opened from an action, or words (`say`: an answer to read — an explanation, steps, a list — or what no action shows) — each with the columns it takes; no cards leaves the screen as it is. The reply is checked whole — every action in the catalog, every input against its action's schema, every card kept one on the screen and kept once, nothing shown twice — by the agent's `output.validate`, and one that does not hold, or does not fit the schema, is corrected inside the same run with what is wrong with it: three answers at most (cortex's `outputRetries`). About 1 s.
  3. **The answer is laid out** in a grid of its columns, each card on the next area with the columns it takes, which the server turns into the layout; a reply with no cards keeps the layout on screen, and a screen has its arrangement (`src/app/arrangements.ts`). The server puts it into the region through the shell's draft (`session.draft`), where moss checks it: the frame with the arrangement in it, one layout taken again for each answer and kept nowhere.
  4. **The plan is placed by the dock,** with nova's `reconcile`: each area holds exactly what the plan lists for it. A canvas that stays keeps its instance and what the person did to it; a card the model writes again is written where it stands. A canvas written onto a screen holds its whole input — what it leaves out is its action's default (`opened`, in `catalog.ts`) — so a card written where another was keeps nothing of it (PLAN.md D12). An answer that changes nothing adds nothing to the stack; the chip still names what was asked. What the model said back is under the chip until the next message. A screen opened, or back or forward pressed, while an answer streams in is what is shown: that answer is no longer placed.
  5. **The answer streams in.** Cortex hands the composer the reply as solid parses it, while the model writes it. Once a card is followed by the next it is finished, and it takes its place if its own checks pass; a place after it holds what it held until the reply writes it, unless that card was kept into an earlier place; a screen comes with the whole reply; the dock re-reads the answer so far (`answers.current`) whenever the message `answer-moved` says it moved. Whether the whole reply holds is checked when it ends. A correction, or a run that ends without an answer, puts the screen back as it was.
- **A message that gets no screen leaves the screen as it is,** and the line says why: the model's reply did not fit, it could not be reached, or there is no key.
- **The model may take 8 s.**
- **Every message is recorded as a run of the model,** through moss (`session.recordRun`): `mira.compose`, with its provider and model, the tokens it spent (`reported: false` where signal estimated them), its steps and how long it took — for the composer, cortex's run meta — and whether it ended in an answer. The server logs a line for each (`src/server/runs/`).
- **An action you add is small, with one purpose:** it says what it shows (`description`), and declares what the model may open it with as a JSON Schema written with zod, every field described; the model's answers are checked against that same schema (`z.fromJSONSchema`). The ones the model may place are `placeable`, in `src/app/action-catalog.ts`.
- **The model never presses anything.** It opens cards with an input — a form filled in — and only the person saves.
- **The keys are in `.env`** (`.env.example` lists them): `GROQ_API_KEY` (gpt-oss-120b; without it, a message is answered with a notice saying so), `MIRA_OWNER`, `RESEND_API_KEY` (without it a link is written to the server's log), `MAIL_FROM`, `PUBLIC_URL` (where a mailed link points) and `DATABASE_URL`.
- **The model is offered what the person may use:** the placeable actions they hold, and the screens whose every action they hold.
- **`src/dev/compose-check.ts` runs the loop offline**, with a scripted model (`src/dev/scripted.ts`), on words, screens and actions the app does not have — so it holds whatever actions the app ships.

## How to proceed from here

First the interview: PLAN.md's open items, each answered or delegated by name (the rulebook's "Before any code").

**Then build in PLAN.md's order of work,** each step checked before the next: your tables, reads and writes; your actions, each placeable one in `placeable` and every one granted in the charter's `actions`; your screens; and a check for each feature in `src/dev/`.
